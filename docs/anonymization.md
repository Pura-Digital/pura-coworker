# Native local anonymization

Anonymization is enabled separately for each Pura LLM / multiple-model setup. New and cloned setups start disabled; Ollama is excluded. Model files are downloaded once from a pinned Hugging Face revision with SHA-256 validation, and shared between setups.

The private CPU worker contains the pinned rizzo-pii neural detector, overlapping text chunking bounded by the actual tokenizer budget (including dense URLs/code), and deterministic detectors. No upstream web server or dictionary files are used. The worker communicates over stdio and loads only local model files with Hugging Face telemetry/network access disabled.

## Data boundary

The gateway operates in Electron's main process on copies of prompts, history, tool results, tool argument string values and descriptive schema fields. Auxiliary completions, memory embeddings and SDK compaction use the same boundary. Original content is retained locally; response text, reasoning and tool arguments are restored before UI events and tool execution.

Archiveye retrieval follows the same MCP boundary. Searches receive the restored original query, and documents and retrieved top-k results remain readable in the tool output and local transcript. Before each LLM call, the gateway masks the selected snippets and their textual metadata (including document titles), together with the rest of the context. This also covers text embedded in MCP resource results and JSON results. Repeated values use the same chat-scoped references across the query and snippets; the answer is restored before display. Search indexing and stored documents are not modified. Enabling this setting protects the LLM payload; Archiveye itself still handles the original query and documents.

Matching lives in `userData/anonymization/matching.sqlite`. Each chat has a separate random token namespace; values use AES-256-GCM with chat/token binding, lookup keys use HMAC, and the encryption key is protected by Electron `safeStorage` (macOS Keychain / Windows DPAPI). No plaintext-key fallback is used. Deleting a chat removes its matching; deleting encrypted rows still works if the key is unavailable.

Text files, PDFs with extractable text and text-only DOCX/PPTX/XLSX files are supported. Images, audio, scans, unreadable/encrypted/mixed-media documents, text beyond the supported size and low-confidence detections require a decision. There is no OCR or transcription. Personal values used as structured keys also require a decision, because protocol/schema keys remain stable. Response tool-argument keys are restored when the model uses a reference there. A decision applies only to unchanged content in the current chat run. New content or a new run requires a new decision. Concurrent requests for the same complex content share one pending decision. Cancelling a decision cancels other pending decisions and follow-up operations belonging to that same request; a new request remains independent.

Service failures offer proceed without anonymization, cancel and restart. Restart stays loading until it succeeds or fails. Complex inputs offer retry, exclude, cancel and proceed in clear text. Excluding all user content cancels the request. Unknown response references require a decision before releasing them; retry regenerates a protected answer, proceeding repeats that call in clear text, and exclusion prevents tool execution from that answer.

Repeated service failures from one user request share one decision, including the answer, automatic title and queued memory ingestion originating from that request. Proceed/cancel applies to those related operations only, as stated in the dialog. A new user request or another chat asks again; complex cases still require their own content-scoped decision. Memory ingestion captures its originating request before enqueueing, so queue execution cannot inherit another request's consent. The decision dialog uses opaque colors in both themes, including native glass mode.

Provider streams retain the request that created them even when SDK callbacks execute outside its async context. Optional title/memory completions are suspended while the local service is not ready; they do not open another service-failure decision or ask for system storage access. They still use the protected gateway when available.

Built-in Computer Use vision requests obtain consent for each new screenshot/prompt through a loopback-only broker with a short-lived chat/tool capability. The capability is revoked on cancellation and never included in provider payloads or tool logs. Human waits do not trigger automatic MCP retries. Existing Pura realtime voice also requires a separate decision before connecting when protection is enabled; a clear-text exception covers only that voice connection until disconnect, with a visible voice badge. It does not disable text-chat protection.

Model detection is probabilistic. All supported categories are enabled, including amounts and dates, which can affect reasoning on hidden values. Arbitrary third-party tools and external service uploads retain their own permission boundaries. Calls without a reliable chat identity are refused when protection is enabled; background operations with a chat identity wait for a user decision when needed.

## Development and packaging

Before the first protected request, Aiden requests system storage access. On macOS the bundled `Aiden Keychain Access.app` is launched through Launch Services with an active app event loop. It enables system interaction and calls `SecKeychainUnlock` with no supplied password, allowing macOS to present its native unlock dialog when required. Password entry belongs exclusively to SecurityAgent; the helper never reads passwords or keychain item values. Only an authorization result/status is returned in a temporary private directory; cancellation removes that directory and terminates the helper. Electron then requests access to its encryption item through `safeStorage`. Concurrent requests share initialization. If authorization is declined or unavailable, the request stays blocked with an in-app “Authorize and restart Aiden” action. If macOS rejects that recovery call, Aiden opens the system's Keychain Access utility and keeps the same decision waiting; it does not relaunch or bypass protection. Relaunch is explicit because Electron 35 caches failed key derivation for the lifetime of a process. Windows requests no separate password: DPAPI initialization is automatic, with an explicit “Restart Aiden” action on failure. The three service-failure choices remain proceed, cancel and recovery, with a loading state during recovery. Existing keys and matching databases are preserved. Native service smoke tests cover download and inference; system storage must also be verified on each actual application runtime. A damaged or inaccessible system keychain can reject the native authorization call without showing a dialog, so in-app recovery does not imply that every system failure can be repaired automatically.

`npm run prepare:anonymization` builds the private PyInstaller worker using Python 3.11/3.12. It is included in `dev` and `build`, and skipped when unchanged. End users need no Python installation. Build each OS/architecture natively; release CI builds Apple Silicon, Intel and Windows workers before packaging. Intel macOS uses the last compatible PyTorch wheel with eager CPU attention. The upstream source commit and license are in `resources/anonymization/vendor/`.

Run `npm run test:anonymization:smoke -- --download` after preparing the worker to test the real download, integrity checks, offline inference, text extraction and restart. To reuse downloaded test weights, put them in `.cache/anonymization-model`, or set `AIDEN_PII_SMOKE_MODEL_PATH`, and omit `--download`. Tests use temporary app data and delete it afterward.

Ordinary Vitest tests cover matching encryption/isolation, setup persistence, streaming restoration, tool arguments, failure decisions, cancellation and vision capabilities. If better-sqlite3 is compiled for Electron, run Vitest with `ELECTRON_RUN_AS_NODE=1` using the Electron executable; CI rebuilds the native module for its Node test runner.

The provider boundary projects SDK tool objects to `name`, `description` and `parameters`; local executors and tool-result `details` stay local. A cancelled privacy decision before an upstream call is an abort, not an empty successful provider response. Preparation failures report the failing phase and controlled model/service state, never raw context or arbitrary exception messages.

Run `node scripts/test-anonymization-gateway-smoke.js` with an Electron-compatible `better-sqlite3` build (`npm run rebuild`) to verify the real SDK loop, native offline model, OS-protected encrypted matching, restored tool execution and restored responses. This test uses synthetic data and a local provider stub; all network calls are forbidden. Ambiguous synthetic SDK instruction metadata is explicitly excluded by the test decision handler; clear-text bypass is never authorized. The smoke test also verifies that cancelling an unsupported input does not call the provider or become an empty-success error. It does not test cloud-provider availability.
